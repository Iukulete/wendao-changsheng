# 仙舟家园混合架构提案：让人物可信，让成本可测

> 2026-10-21 · 方案评审稿，未实施。适用当前 3D 移动仙舟家园，不恢复旧卡片/六纪元运行时。
>
> 本稿补充 `ARK_ARCHITECTURE_REVIEW.md`，响应新的评估标准：**以人物体验、帧时间、吞吐量、内存、可维护性和实测结果决定架构，不以代码行数、模式数量或 C++ 占比评分。** 本次只新增文档；没有安装工具链、编写原生扩展、切换渲染器或修改存档。

## 一页结论

**我建议采用“数据统一、行为分层、预算调度、计算可替换”的混合架构。** GDScript、C++ GDExtension 和 GPU Shader 各做擅长的工作，而不是把同一套逐人逐帧逻辑翻译成三种语言。

1. **人物层用 GDScript 和配置资源**：身份、偏好、承诺、记忆、关系、生活规则与可创作内容；Godot 场景负责可见人物、动画、碰撞、交互。
2. **模拟层采用 DOD 与 ECS 思想**：稳定实体 ID、按用途分组的数据、批量计算、明确写入者；不要求先引入完整 ECS 库。人仍是有个性的角色，不是只有数值的工人。
3. **行为层选择 Utility → 有限 GOAP → 分层状态机**：先决定“现在最想做什么”，必要时规划“怎样完成”，最后可靠执行“走过去、拿起、等待、交付”。日常简单目标不启动规划器。
4. **调度层采用事件唤醒、分层更新和有预算的批任务**：近处重要人物精细表现，远处保留事实但简化模拟。线程只计算快照，不直接改场景；结果经主线程校验后提交。
5. **C++ 是可替换的批计算后端**：优先候选是感知候选筛选、目标评分、规划搜索、路径图搜索；先证明热点在哪，再把同一输入输出契约下的计算核原生化。
6. **GPU 做海面表现**：当前海面已经是 Shader。近期保持 GL Compatibility 的顶点/片元路线；计算着色器、FFT 海浪或改用 Forward+ 属于另一个有数据门槛的决策，不是混合架构的默认前提。

这不是“全部都要上”。**推荐的是这些边界及其组合方式，是否启用每个复杂组件由后文门槛决定。** 简单实现满足体验和性能时，它就是合格实现。

## 1. 证据边界：知道什么，还不知道什么

**本次未新增性能实测。** 下面所有人口规模、毫秒预算、更新频率和验收阈值都是待验证的提案。当前没有确认最低配置、目标分辨率、帧率与同时可见人口；不把用户拥有的某块显卡当作产品最低配置。

### 四个优先验证的假设

- **H1 导航尖峰**：多人在清晨/风暴/改家具后同时重建网格，可能比评分公式更昂贵。先分开测“环境采样、建图、搜索、跟随”，再考虑 C++。
- **H2 全量遍历**：资源/交互列表随地图扩张，全量扫描可能放大感知与任务选择成本；先测空间索引和脏标记，而不是直接原生化循环。
- **H3 世界同步尖峰**：时段推进、保存、区域唤醒可能聚集在一帧；平均 FPS 会隐藏这个问题。
- **H4 海面像素成本**：大面积水面、反射、透明叠层或高分辨率可能压 GPU；当前轻量占位不能代表正式海面的负载。

这些是可证伪的假设，不是已定位的瓶颈。

## 2. 先定义“有人情味”的技术含义

人物可信不是每帧重新思考，也不是随机说更多话。建议人物模型至少表达：

| 层面 | 最小可用表达 | 玩家能看见的结果 |
| --- | --- | --- |
| 身份和偏好 | 技能、作息、珍视的物件、愿意/不愿意做的事 | 同样下雨，有人收帆，有人先照看灯，不是换名字的同一行为 |
| 当前需求与承诺 | 疲劳/受寒、正在搬的东西、答应修理、赴约时间 | 不会为多一点收益丢下半途的工作；紧急危险又能合理打断 |
| 经历与知识 | 事件 ID、亲历/被告知来源、涉及的人、重要性 | 只记得自己经历或可靠获知的事；没在场的人不突然引用整段往事 |
| 关系 | 实际发生过的帮助、分歧、信任依据与界限 | 会给特定人留饭、婉拒危险差事、记得对方喜欢坐哪；不只是一条好感值 |
| 表达 | 动作、朝向、等候、短对白、私人空间与纪念物 | 看见玩家回家会抬头；等同伴落座再开饭；旧承诺落实到家中变化 |

**推荐先做“有承诺的一顿饭”作为人物试验场**：两位居民因偏好和当前事务作不同选择；有人先忙完工作再来，有人留一份热汤；风暴会打断，但读档不会忘约、凭空知道秘密或重复扣食物。沿用当前共餐的到场核验，不以 AI 生成的计划直接判定大家已经吃完。

长期记忆采用“重要事实 + 少量近期细节”：承诺、关键帮助、拒绝和共同经历保留；低价值重复细节可以压缩。关系按实际接触建立稀疏连接，不预建所有 NPC 两两关系表。世界真相与某人的知识分开；重要事实的遗忘/传闻应是明确玩法规则，不能只是缓存被淘汰的副作用。

验收既看性能，也看观察：新玩家能否说出“她为什么现在这样做、她与另一位有什么不同”；记录违背承诺、行为来回切换、重复对白、无原因呆站、错误记忆与穿帮次数。行为数量更多不自动算改善。

### 允许改旧设计：保留体验目标，不固守原来的实现

用户已允许以体验为主调整原架构，因此不把旧草案的每条规则都当成不能动的约束。我会优先评估这些调整，但不会在迁移收尾时夹带未经验证的大改：

| 候选调整 | 为什么值得改变 | 小范围 A/B 与风险 |
| --- | --- | --- |
| 从“所有资源永久采完”扩为“遗迹奖励唯一 + 部分生态资源可恢复” | 永久有限很适合当前防复制样板，但长期生活若只剩空资源点，居民自主性会退化成无事可做 | 只试一个有恢复条件/容量的潮池或真实补货点；记录生态库存与采出量，不每日凭空刷新。观察探索动力与居民生活连续性，防止变成无限挂机收入 |
| 从天气阶段一刀切禁止启航，改为船况、航道与可读风险决定 | 保留损坏船体需要修理的因果，但让“有风险仍可出发”与自由探索一致 | 在受保护测试海域比较“强制等雨后”和“允许承担已提示风险”；看新手理解、可撤回性和挫败感。不是取消碰撞/船况，也不是取消安全提示 |
| 将最终时间/天气归到统一的游戏内日历，而非永久依赖独立的 T/R 灰盒按钮 | 人物作息、天气与航行后果有共同时间依据，更容易表现自然生活 | 先试一段航行/休息触发的明确时间推进；验证不会跳过未完成交付、强迫每日劳动或引入现实离线催促。原按钮可保留为开发调试入口 |
| 远处采用语义模拟，而非要求全世界逐帧实体运动 | 让“世界有人生活”不以维持远处全部模型/路径为代价 | 对照真实实体运行的同一任务，比较货物、耗时、关系和返回位置；若玩家能看出跳变，缩小启用范围，不用降级掩盖穿帮 |

这些变化都需要保留“能解释的来源、人物自主性、可恢复后果”。不因性能优化把居民变成产出按钮，不自动拼接旧剧情，也不把即时大模型对话当作人物可信的默认解决方案。

## 3. 推荐的整体结构：一个事实来源，两种计算后端

```text
内容定义（GDScript + Resource；身份、偏好、动作、物件、地点）
                         ↓
权威模拟状态（稳定 ID；居民/船/资源/任务/关系/记忆；单一提交入口）
        ↓ 只读快照                         ↑ 校验后提交命令
预算调度器 ──→ 感知候选 → Utility → 按需 GOAP → 动作意图
        │          GDScript 参考后端 / C++ 批计算后端
        │                 （后台不接触活跃场景）
        ↓
Godot 主线程：动作执行、角色物理、船岸转换、动画/交互、存档提交
        ↓ 已发生事实
人物记忆 / 关系 / 日程 / UI / 音效响应

Godot 渲染 → GPU 海面/材质/特效（不拥有资源、任务与人物事实）
```

### 数据所有权

- **模拟状态是事实源，场景是表现与执行接口**：某居民的任务与库存不会同时由 Node、C++ 和 UI 各维护一份权威副本。物理移动由主线程角色执行，在约定 tick 写回权威位置；渲染插值位置不反过来改账。
- **DOD（面向数据设计）**：将经常一起计算的数据紧凑排列，例如位置、所属区域、行动状态、下次更新时间；文字、人物设定、长记忆另存。重点是减少不必要读取和重复计算，不是给所有东西换类名。
- **ECS 思想**：实体用 ID，能力/状态按组件组织，系统按批处理；近期采用适合本项目的少量组件列即可。完整 ECS 库要另证明实体增删、查询、编辑工具与存档集成的净收益，不因名字高级而直接装入。
- **同一计算契约可替换**：例如 `score_goals(snapshot, actor_ids) → scores/reasons`；先有 GDScript 正确性基线，再 A/B 比较 C++。原生接口按批传紧凑数组，避免每 NPC 每帧跨语言查询几十个属性；拷贝、封送和提交时间也计入收益。

稳定身份分两层：存档使用不变的 `resident_id/vessel_id/fixture_instance_id/resource_id`；运行时索引用 `slot + generation`，防止某对象删除后新对象复用槽位，旧任务误作用于新人。NPC 个性配置仍可编辑，不需要把所有故事条件编译进 C++。

**优先迁移对象不是“整个游戏”，而是一条采集/共餐/修理任务的状态和接口。** 保留现有 JSON 文件保护、历史 schema 和资源 ID；存档只保存已提交事实及未完成任务语义，不保存线程 ID、指针、搜索队列或 GPU 缓冲。旧档不能凭空获得关系或记忆；加载后按已保存目标恢复或重规划。

## 4. 人物决策：三层各管一件事

### 4.1 Utility：在少量可行目标中选“现在做什么”

先由权限、能力、安全和人物边界过滤，再对休息、工作、共餐、照看同伴等候选计算分数。偏好、距离、当前需求、日程和承诺是因素；不要用“收益最高”覆盖人物意愿。

为避免反复横跳，设置持续行动奖励、换目标门槛、合理的最短承诺时间与冷却；紧急安全可打断这些约束。随机变化使用可重现种子与有限扰动，不每帧掷骰子。调试面板显示候选前三名、分数理由与否决原因。

用效用比较不同目标有成熟实践，但本项目的分数、滞回与承诺规则需要自己的体验测试，不直接照搬其他游戏。[Mark / Dill：Utility Theory 原始演讲](https://media.gdcvault.com/gdc10/slides/MarkDill_ImprovingAIUtilityTheory.pdf)

### 4.2 有限 GOAP：只为确实存在替代路径的目标规划

GOAP 可理解为“给定目标，组合满足前提的动作”。例如“让受寒同伴得到热食”：锅边已有汤则端过去；没有汤但有材料且允许使用灶具，则取料、做汤、端过去；缺材料或对方拒绝，则不能凭空完成。

**明确限制**：按目标提供小动作集合；只读角色已知事实；动作有前提、预计成本和效果；最大搜索展开数、计划长度、取消检查和总任务预算均可配置。可先试 `128` 次展开、`6` 步上限——只是实验参数，不是容量结论。简单“去睡觉/继续手中工作”走直接动作链；只在目标改变、前提失效或计划完成时重规划，不每帧搜索整个世界。

计划中的“效果”只是预测，**只有执行层实际成功才提交事实**。搜索超限或无解时保留安全的既有行动、等待或报告缺少条件；不得假装送达。原始 GOAP 研究支持用目标、前提、效果构成可组合行动；上述预算和领域边界是本项目建议。[Jeff Orkin：实时游戏规划研究](https://cdn.aaai.org/Workshops/2004/WS-04-04/WS04-04-006.pdf)

### 4.3 分层状态机执行：把计划变成可中断的真实行为

选择 **分层状态机（HFSM）作为第一版执行骨架**，不是再同时建立一套通用行为树框架：

```text
生活目标：准备共餐
  当前动作：带汤到桌边
    移动 → 占用使用位 → 播放拿放动作 → 核验到场 → 提交一次交付
  中断：危险 / 对方离开 / 通路失效 / 玩家启航
```

每个动作定义 `开始、更新、成功、失败、取消、恢复`，持有资源/座位预留凭据；取消释放预留，已经取得的货物不能消失。事件 ID/事务 ID 保证重复回调不重复扣货或记功。社交互动是双方接受并预留位置的共同任务，不由一方直接强制改另一人的脑子。

以后若大量动作子流程需要复用条件/顺序/选择，可只在动作内部评估行为树；它必须减少具体的重复和错误，不能和 Utility、GOAP 同时争夺最高决策权。

## 5. 分层更新与 Job System：减少无效工作，保证关键反应

### 5.1 三种时间与三个模拟等级

区分 **画面时间、固定物理 tick、游戏内日历**。降低 AI 决策频率不等于降低玩家移动/碰撞频率。当前 `T`/休息与 `R` 的时段/天气推进语义先保留；是否改连续日历另行设计，不能因为引入后台任务就出现现实离线收益。

以下频率仅为首轮可调试验值：

| 等级 | 谁在里面 | 更新方式 | 绝不能省掉的事实 |
| --- | --- | --- | --- |
| Active：玩家正在观察/互动、同舟重要人物、紧急危险相关者 | 不只按摄像机可见性；近身门后的人也可能重要 | 运动/碰撞走正常物理 tick；目标选择约 2–5 Hz，并由关键事件立即标脏；动画按显示需求更新 | 真实到达、碰撞、人物反应、手中货物、承诺与同伴协作 |
| Near：附近但非焦点 | 可很快进入视野的生活区/岸边人物 | 目标选择约 0.5–1 Hz，路线按需求更新；降低无关动画细节但维持位置连续 | 资源竞争、路线有效性、工作进度、突然出现玩家时的恢复 |
| Far：不可观察的远处船/地区 | 保留实体身份，不保留每帧完整场景表现 | 按相关事件或游戏内时段做聚合模拟；必要时保存路线段及进度，而非逐步寻路 | 有限货源、劳动/维护消耗、船员同意、天气风险、库存守恒与故事事实 |

分层要有进入/退出滞回、预热和重要人物固定优先级，防止镜头转动导致反复卸载。远处并非凭空发收益：聚合运输仍需合法路线、投入和时间，先预留再结算，切回实体时必须与货物/位置/承诺一致。玩家即将看见的最终交付应转回实体执行，不能眼前瞬移。

正在参与玩家交谈、共同用餐、重要关系抉择或关键剧情的人物应锁定在必要的高精度等级；不能为了通过压测把他们静默降成 Far，再偷偷完成一次关系变化。远处人物获知消息仍需传播来源，镜头外不等于全知。

远处语义模拟与当前“可观察实体全过程”并不完全相同，**先在测试场证明边界，再由产品评审决定启用范围**。同样规模同时出现在玩家面前时，不能偷偷把其中大多数降为 Far 来宣称支持该人口。

### 5.2 事件唤醒 + 预算队列，而不是事件风暴

- 感知先用区域/船/空间格索引找候选，再做必要的视线、距离与权限检查；不让每个人扫描全世界或互相两两比较。
- 时段、天气、资源、关系、家具变化只通知相关订阅者。重复的“需重新选择目标/需重算路线”可合并；采集、交付、产权、记忆等事实事件不能随便合并或丢掉。
- 每帧设置提交与请求预算，非紧急工作错峰；队列按危险、玩家相关性、等待年龄排序，避免远处任务永远饿死。
- **背压**就是“工作来得比处理快时如何收敛”：合并重复请求、丢弃过期计算结果、限制新规划、延迟非关键表现；不丢交易事实。队列持续增长必须报警并降低被批准的模拟负载，而非无限堆内存。
- 关键事实通道也有容量与监测；不足时在提交前延后/拒绝新的事务，不能先扣货再扔掉事件。已提交事实由权威状态保障，低优先级显示通知可以稍后补齐。
- 安全反射与必要碰撞走主线程快速路径；高层“找更优办法”可晚一些。不能为了异步而让 NPC 被危险击中后还等一个排队计划才反应。

### 5.3 后台只计算快照，主线程提交事实

```text
主线程 tick：收集变化 → 构造相关数据快照 → 分批提交计算
后台任务：只读输入 → 有界计算 → 输出意图/路径/评分
主线程后续 tick：检查版本与前提 → 原子提交 → 发出已完成事件
```

任务头建议包含 `session_epoch、entity_id、generation、job_revision、topology_revision、request_id`；有目标资源时再带其版本。读档、居民改目标、拆家具、资源被抢或实体移除后，旧结果即使完成也不能生效。**船整体移动不应无条件废弃甲板本地路线**；船岸转换另检查停泊/接驳版本。

避免每帧复制整个世界；按变更和相关实体构造只读数据块，输出写入任务独有缓冲，完成前不复用。主线程在有限提交窗口复核目标、预留、材料和权限，真正发生的交易使用唯一事务 ID。`call_deferred()` 只解决调用时机，不自动解决过期结果、双交付或队列爆炸。

首选 Godot 自带 `WorkerThreadPool` 执行足够粗的批任务，不给每个 NPC 建线程，不另起线程池和引擎争满所有核心。小任务可能因调度成本反而变慢；完成任务需要回收，不能只提交不收尾。应先检测完成，再在非阻塞路径取结果并完成清理；退出场景/关游戏时停止接单、协作取消、等待已启动任务退出。所谓取消通常是任务主动检查标记或放弃结果，不是强行杀线程。[Godot 4.7：WorkerThreadPool](https://docs.godotengine.org/en/4.7/classes/class_workerthreadpool.html)

**Godot 4.7 的线程边界**：活跃 SceneTree 不可由工作线程任意修改；物理线程安全有专门设置；本方案不把当前 `direct_space_state` 射线/碰撞代码原样搬进工作线程。导航 Server 支持并行查询，但同一个 `AStarGrid2D` 不能被多个线程同时操作；可采用每任务独占搜索状态和只读图数据。优先保守地把传感/碰撞采样留在主线程，搜索只处理缓存图；使用 Server 并行 API 时另做版本与压力测试。[Godot 4.7：线程安全 API](https://docs.godotengine.org/en/4.7/tutorials/performance/thread_safe_apis.html)

### 可重现性，不承诺跨平台物理逐位一致

固定逻辑 tick、稳定实体排序、独立随机种子与确定的同分规则；记录输入事件、被接受的任务结果、提交 tick、失败原因和版本。调试重放可使用记录过的接受顺序，参考后端可单线程运行。仅有随机种子并不能消除线程完成先后差异；Godot 物理、浮点和 GPU 也不能因此被宣称跨平台逐位确定。比较后端时，整数账目/ID 必须一致，浮点量用明确容差，并检查目标排序是否因此改变。

## 6. 移动仙舟导航：世界图 + 船内图 + 明确转移

**推荐分层导航，而不是一张不断重烘焙的全世界 NavMesh。**

1. **宏观图**：岛、泊位、船和航道的连接关系，用于“去哪/是否能到”；远处任务走路线段进度。
2. **局部通行图**：岸上使用区域地形图/适合的 Godot 导航；船上使用 `vessel_id + deck_id` 的本地通行图。近期先缓存现有甲板网格，家具确认、门/梯变化或拆建时更新相关区域，避免每人重做相同物理采样。
3. **连接点**：门、梯、跳板、登舟点是有条件/容量的 portal。船岸连接只有距离、朝向、停泊状态和入口有效时开放；启航撤销连接，人物在连接上的处理必须明确，不能落在海里才补救。
4. **实际运动**：角色根据下一局部目标移动；动态避让、窄门预约与失败恢复在此处理。导航给出路线不等于角色已经碰撞安全地走完。

坐标契约：海域/船体用世界变换；甲板人物、家具、锚点与路线使用船内坐标；通过 portal 时集中转换。保存当前空间 ID、局部位置、语义目标与携货；加载后重算路径，不保存过期路径数组作权威。

路径缓存至少按空间、拓扑版本、起终区域和角色通行能力区分。家具移动增加 `build_revision`，只影响相关图与路线；门状态改变增加连接版本；船平移/转向只改变局部→世界变换，不重算所有甲板路径。若使用公共共享图，后台读取的是完成发布的版本，不边改边查。

`NavigationAgent3D` 是可选执行辅助，不会自动移动角色；其避让与寻路、物理碰撞是不同问题。需要单独测坡面、窄道对向、门口等待、登舟与船转向，不能把“加入 NavigationAgent”当作验收。[Godot 4.7：NavigationAgents](https://docs.godotengine.org/en/4.7/tutorials/navigation/navigation_using_navigationagents.html)

## 7. 海面：先分清画面、物理和 GPU 预算

### 推荐的首条路线

- 保留 GL Compatibility，建立可切换海面质量档：小成本顶点波动、法线/高光、有限泡沫/岸线表达；远处降低网格/材质细节。以固定机位、日夜、风雨与海平线连续性评审，不先追求算法名称。
- 测量水面占屏比例、分辨率、网格细分、片元材质、反射和透明层数的影响。分别做同网格简化材质、各效果开关、全海/近岸/室内视角对照；单纯隐藏水面会改变遮挡，不能把那一个差值全部归因于 Shader 算术。
- **画面海浪不直接拥有物理真相**。目前玩法以 `WATER_SURFACE_Y` 等规则判断水面，Shader 做轻微视觉波动。若将来海浪影响浮力，采用同一套时间/参数的低频 CPU 波面查询，仅采样船体需要的点；细碎波纹仍只在 GPU。控制误差、脚底/船边穿帮与成本，避免每帧回读整张 GPU 高度图或重建海面碰撞。

### Compute / FFT 的升级条件

Godot 4.7 的计算着色器需要 RenderingDevice 后端，即 Forward+ 或 Mobile；**GL Compatibility 不支持这条 Compute 路线**。普通顶点/片元 Shader 仍是 GPU 程序，所以“使用 GPU”不意味着必须换后端。切换渲染器还可能需要调整灯光/环境，不能只换一个开关并沿用旧画质结论。[Godot 4.7：Compute Shader](https://docs.godotengine.org/en/4.7/tutorials/shaders/compute_shaders.html)、[渲染器差异](https://docs.godotengine.org/en/4.7/tutorials/rendering/renderers.html)

只有当正式美术样板证明需要现方案无法合理表达的波谱/互动效果，并且目标设备上的 A/B 表明新方案在画质、GPU 时间、显存和兼容性上可接受，才评审 Compute/FFT 与后端升级。GPU 结果即时同步回 CPU 会引入等待；官方示例也提示避免提交后立刻同步。人物权利、库存和剧情不适合被绑到这种 GPU 回读依赖上。[Godot 4.7：Compute 同步注意事项](https://docs.godotengine.org/en/4.7/tutorials/shaders/compute_shaders.html#execute-a-compute-shader)

## 8. 测量方案：先建立真实容量曲线

### 8.1 基准场景与人口，不报“理论支持人数”

保留当前两居民+琼华舫样板作功能基线。另建隔离测试场，在相同设施/资源/行为复杂度下逐级加人口；人偶闲站不能代表生活模拟。

| 试验档 | 总人口与分布示例 | 主要回答的问题 |
| --- | --- | --- |
| N10 | 10 Active | 人物选择/到场/交流是否可信，单次路径/规划成本多少 |
| N50 | 20 Active + 30 Near；另跑 50 全 Active | 分层节省了什么；真实可见人群上限在哪里 |
| N200 | 30 Active + 70 Near + 100 Far；另跑 200 全 Active 压力档 | 队列、拥挤、动画/碰撞、区域转换各自怎样扩展；全 Active 可以失败，但要说明失败位置 |
| N1000（后续压力探针） | 30 Active + 70 Near + 900 Far | 远处世界状态、内存、时段结算能否增长，而不是宣称能同屏 1000 人 |

以上档位不是承诺的产品人口。每档都跑：正常生活、全员受天气影响、清晨集中出工、窄门/共餐拥挤、连续搬家具、启航召回、目标被抢、途中读档、从远处突然接近，以及多次进出区域的内存稳定性。不能只跑“稳定工作且从不被打断”的最好情况。

### 8.2 怎么测才可比较

- 锁定引擎版本、提交、操作系统、CPU/GPU、驱动、电源模式、渲染后端、实际内部渲染分辨率、窗口/全屏、画质、VSync/帧率限制、人口分布与资源版本。
- 功能先在现有测试链通过。性能使用同等优化构建，固定种子/输入轨迹/相机；准备期与稳定期分开记录。建议预热 30 秒、采样 180 秒、交错 A/B 各至少 5 次，同时保留首次载入/首次 Shader 编译尖峰；这些是起始方法，可按噪声调整。
- 先做离屏/无渲染计算基准定位 CPU，再做真实显示下的端到端测试；最终容量由后者决定。云端 llvmpipe 可做功能/趋势排查，不作为目标 GPU 的验收机。
- 脚本/物理看普通 Profiler；渲染 CPU/GPU 看 Visual Profiler，必要时补平台工具。Visual Profiler 的 CPU 数据不包含脚本与物理；对照时必须保持 viewport 一致。原生后台工作另设自有计时/追踪，不能因脚本 profiler 看不见就当作零成本。[Godot 4.7：Profiler 与 Visual Profiler](https://docs.godotengine.org/en/4.7/tutorials/scripting/debug/debugger_panel.html)

### 8.3 必须采集的指标

| 类别 | 指标与解释 |
| --- | --- |
| 帧流畅度 | 帧时间 p50/p95/p99、最大值、超过 16.67/33.3/100 ms 的帧数和发生场景；分位数表示有多少帧比它更快，不只看平均 FPS |
| CPU/GPU | 主线程、物理、渲染提交、GPU 各自耗时；工作线程 CPU 总工作量与墙钟时间分开，不把并行耗时相加当成帧时间 |
| AI 吞吐与延迟 | 每秒完成的有效决策/计划、每个计划展开数、成功/无解/超限率；真实任务完成率、取消率与原因、重规划率、重复认领/交付次数；事件到可见反应 p95/p99、任务队列等待、最老任务年龄、丢弃过期结果比例 |
| 导航 | 每秒请求/完成数；采样、建图、搜索、缓存命中分别计时；排队延迟、重规划原因、卡住/穿墙/无法到达率与拥挤等待 |
| 世界模拟 | 每次时段推进耗时、涉及实体数、货物转移次数、区域激活耗时、从 Far 恢复成本；重复结算/库存守恒失败必须为零 |
| 内存 | 进程常驻内存/峰值、模拟数据、记忆/关系、快照和队列高水位、每档人口的增量、显存与资产驻留；重复进出后是否持续增长 |
| 内容维护 | 给第三位居民增加同类行为所需的修改点/实际工时、定位一次卡住原因的时间、构建/打包成本、跨平台失败；不是数类或数 C++ 行 |
| 人物体验 | 目标抖动、承诺中断、无解释等待、重复对白、错误记忆、眼前瞬移、社交拒绝失效；盲测比较“为什么这么做”和人物辨识，而非用动作总数代替体验 |

### 8.4 临时预算：用于开工对齐，不是实测成绩

**未确认目标平台前，暂用 1080p / 60 FPS 作为一种基准提案**；它不覆盖用户最终分辨率和硬件要求。16.67 ms 是 60 FPS 的每帧时间，CPU 与 GPU 通常存在流水重叠，不能简单相加；仍需观测端到端呈现。

| 项目 | 起始试验门槛/预算 | 说明 |
| --- | --- | --- |
| 端到端稳定场景 | p95 ≤ 16.67 ms；p99 ≤ 20 ms，并单列所有 >33.3 ms 尖峰 | 允许的抖动需体验评审；不是保证每帧 60 FPS |
| 主线程 / GPU | 各自 p95 先争取 ≤12 ms | 给不可预测波动留余量；不是把二者相加后要求 24 ms |
| 主线程生活系统 | AI 调度/快照/提交 ≤1.5 ms，导航相关提交/必要采样 ≤1.5 ms，世界/记忆事件 ≤1 ms | 分项是设计分配，不是实测分位数之和；其余留给玩家/物理、动画、渲染提交/UI/音频等，必须整体复核 |
| 海面 GPU 增量 | 同几何/机位的对照先以 ≤2 ms 为样板预算 | 包括启用的水效果；真实显卡实测，不套用云端数值 |
| Active 关键反应 | 安全检查下个物理 tick 可处理；高层意图响应 p95 先以 ≤150 ms 为候选 | “处理安全事件”不等于一帧算完逃生路线；普通生活可更慢，但需有可见连续动作 |
| 队列与内存 | 持续负载下不无限增长；临界档必须报告具体上限/峰值 | 在确认硬件前不捏造 RAM/显存总额；先按状态规模给出增长曲线 |

若预算不满足，先说明是哪一阶段、哪档内容超支，再选择方案。不能通过删除角色个性、隐藏失败或降低未披露画质来“达标”。

## 9. 复杂组件的准入门槛

“证明有用”可以是更可靠、更好创作或更可信的体验，不要求每项都只证明速度；但要先声明要改善哪项，并交付对照证据。

| 组件 | 必须解决的具体问题 | 对照与采用条件 |
| --- | --- | --- |
| DOD 批数据/空间索引 | 全量扫描、重复取属性、快照成本或多实体一致性 | 同输入结果正确；吞吐/内存/修改成本中至少预先指定的一项明显改善，帧尾延迟不恶化 |
| Utility | 多种需求/偏好与承诺竞争，硬编码优先顺序难表现人物差异 | 与原日程对照：理由可解释、人物可辨认、抖动可控；无提升则保留更简单规则 |
| GOAP | 同一目标有多条因条件变化而切换的完成路径 | 与手写动作链对照：缺料/阻路/工具变化时有合法替代，搜索成本受限，新增动作实际减少特殊分支维护；只一条链时不上 |
| 批任务/线程 | 主线程存在可独立计算的热点，单线程预算被突破 | 包含快照、调度、同步、提交后仍降低主线程压力；有效吞吐和队列响应改善，无竞态/内存增长；细任务净亏则不用 |
| C++ GDExtension | 降频、缓存、索引和批处理后仍存在纯计算热点 | 与同算法 GDScript 对照；建议把“热点 p95 改善约20%且超出测试噪声，或在既定延迟预算下提高所需吞吐”作为候选门槛；端到端尾延迟、正确性与维护成本同时过关 |
| 完整 ECS 框架 | 自建组件查询/生命周期维护已成为实测与生产瓶颈 | 用同一实际场景验证查询、增删、内存、编辑/调试、存档和团队成本；不能只展示一百万空实体微基准 |
| Far 模拟 | 总世界人口/地区增长超出实体模拟预算 | 近远切换事实一致、无资源复制、无玩家可见瞬移，原有承诺/关系不断裂；明确披露简化项 |
| Compute 海面/新后端 | 现路线达不到批准的视觉目标或成本要求 | 目标 GPU 上画质与 GPU/显存/兼容性对照成立，且打包/回退测试通过；无证据不切换 |

其中 `20%` 是评审时可调整的实验阈值，不是通用真理。GPU 已是瓶颈时，AI 加速不一定立刻提高 FPS；应检查它是否满足了已声明的 CPU 余量/吞吐目标，而不是只展示孤立的倍数。

## 10. 可执行的小步里程碑

以下均是待批准的小原型，旧玩法 ID、存档与现有回归是护栏；每个原型有开关和简单后端可回退。不在一个 PR 同时改 AI、导航、渲染和存档格式。

1. **测量与行为观察台**：记录上述指标和任务原因，制作 N10/N50 场景；先不改变决策。交付可重放轨迹、原始数据、p50/p95/p99 报告和一段可观察共餐。停止条件：能解释尖峰/卡住来自哪里；测量开销也有开/关对照。
2. **一条人物闭环**：对既有共餐/工作提取权威任务状态，以 Utility + HFSM 表现两位居民的差异、承诺与拒绝；已有日程作 A/B。交付途中保存、风暴、缺食物和同伴缺席测试，不顺带扩世界人口。
3. **一个有替代解的 GOAP 试验**：只选“准备热食”或“修理一处损坏”之一；限制动作域和搜索。与手写链对照，证明条件变化产生合理替代且不过度打断；无明显收益则保留接口，不启用规划。
4. **一条导航/调度热点实验**：按测量结果只选“缓存船内通行图”或“批量候选/评分”作为首项；先单线程 DOD，再后台批任务，再按准入门槛加一小块 C++。提交全链路 A/B，而非直接把所有行为移到原生。途中改家具、启航、读档和任务过期必须可恢复。
5. **扩展与海面分别评审**：人口逐级进入 N200/Far 切换试验；海面另做固定机位质量档对照。两者分开提交，防止 CPU 改动与 GPU 改动互相掩盖。任何后端切换、原生工具链安装或新平台支持都另获授权。

## 11. 原生扩展与维护风险：上线前必须付清的成本

GDExtension 不要求重编整个 Godot 引擎，但仍需要自己的编译、兼容与发布流程；不是把 `.gd` 改后缀就能交付。Godot 官方的 `godot-cpp` 文档说明了扩展/模块区别与版本、浮点精度兼容边界。[Godot 4.7：godot-cpp](https://docs.godotengine.org/en/4.7/tutorials/scripting/cpp/about_godot_cpp.html)

- **锁定工具链**：与项目 Godot 4.7.1 相容的 `godot-cpp` 提交/API、编译器、构建参数和依赖；正式采用前验证实际版本，不直接跟踪开发分支。
- **发布矩阵**：Windows x86_64 的 debug/release 原生库、运行时依赖和导出加载必须测试；云端 Linux 若要跑同一原生回归，还需对应构建。尚未确定的平台不能宣称支持。官方流程也要求为计划支持的平台分别构建。[Godot 4.7：GDExtension 构建与使用](https://docs.godotengine.org/en/4.7/tutorials/scripting/cpp/gdextension_cpp_example.html)
- **真实打包验证**：当前包清单/白名单需要显式纳入扩展及依赖，不能因编辑器能运行就认为发布包完整；测试无开发工具环境启动、存档重载、退出时任务清理，以及扩展缺失时的明确行为。
- **调试成本**：C++ 崩溃、越界、竞态不是普通脚本错误；保留符号、批任务追踪、数据契约校验和单线程参考后端，使用适合平台的内存/竞态检查。不要用共享 Node 指针让两套语言交叉改状态。
- **资产管线同样入预算**：正式角色的骨骼、动画、碰撞、材质与灯光逐批接入；用占位人偶测出的 AI 成本不能当完整角色帧预算。模型视图替换保留实体/交互锚点和存档 ID，资产来源与许可单独验证。

## 最终选择

我推荐的不是“少用先进技术”，也不是“尽量多用 C++”。是：

> **让人物的承诺、记忆和关系构成稳定事实；让 Utility 选择意图、有限 GOAP 找办法、可靠执行层兑现行为；用 DOD、预算与任务系统控制规模；只把被证明昂贵的计算交给 C++，把被证明值得的画面工作交给 GPU。**

先交付一个让人能看懂、愿意相处的居民生活样板和可信的测量台，再用数据决定复杂度。这条路线既保留后期大量 NPC/多舟世界的扩展空间，也允许每一块技术单独证明自己的价值。
