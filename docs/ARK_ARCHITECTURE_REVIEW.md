# 仙舟家园架构评估：保留方向，小步拆分

> 2026-10-21 · 讨论稿，不是重写授权。只评估当前 **3D 移动仙舟家园**：自由探索、模板与自由建造、居民自主生活、成长与后期多舟产业。旧 2D 卡片/六纪元运行时不属于候选方案。
>
> 阅读范围：`PRODUCT_TARGET_CURRENT.md`、`GAME_DESIGN_OPEN_WORLD_ARK_V1.md`、`OPENING_SLICE_DESIGN_V1.md`、`ARK_ITERATION_PLAN.md`，以及当前 Ark 脚本、场景和相关测试源码。工作树处于迁移中，分支为 `codex/dot-ark-stability-audit`；以下用文件和函数定位，避免把正在变化的行号当作依据。本次是静态评估，未执行游戏、性能测试或架构改造。

## 先说结论

**你的核心设计值得保留；需要优化的是“怎样让更多内容接得进来”，不是把游戏换成另一种类型。**

- 产品上，最清晰的主线是：**出去探索 → 带回所得 → 家发生可见变化 → 居民真的使用它 → 有理由再次远行**。移动家园把探索与经营连在一起，是目前最应保护的特色。
- 工程上，当前集中式灰盒适合快速验证，但继续为每件家具、每位居民、每艘船添加一组专用字段，会让修改越来越互相牵连。
- 建议 **先做小范围提取，再逐步采用 Godot 场景 + 配置资源 + 独立运行状态**。不换引擎，不推倒存档，不一次接入完整 ECS、通用 AI 框架或大世界流式加载。

“架构好”只能降低试错和维护成本，不能保证游戏好玩。好不好玩仍需让新玩家实际完成上述循环，再观察他们是否理解、是否愿意继续。

## 一、玩法架构：方向成立，先控制扩张顺序

### 已经形成的优势

1. **空间有意义，而不只是升级数字。** 棚屋庇护、甲板扩建、客舱床位、居民走去共餐，能够把投入变成看得见的生活结果。
2. **探索与家园有因果。** 遗迹奖励会变成罗盘、炉具或风撑；自由前往、预警、撤退与回舟恢复可以共存，不必靠等级门组织地图。
3. **居民与产业有边界。** 有限资源、真实采集、分离货舱，以及客居权/经营权/船体产权分开，给后续多舟社会留下了比“购买一个收益按钮”更好的基础。
4. **模板与自由搭建可以互补。** 模板帮助不善布局的玩家快速安家，自由编辑让玩家保留个性；两者应共用同一套放置规则，而不是两套玩法互相绕过校验。

### 最值得一起确认的三处取舍

| 问题 | 建议讨论的默认方向 | 代价与限制 |
| --- | --- | --- |
| 下一轮做更多系统，还是把一段生活做深？ | 优先已有家具编辑、真实床位和第二位居民使用空间；每轮必须能玩出一个新结果 | 地图和内容数量增长较慢，但能较早发现“家是否真有用” |
| 自由建造有多自由？ | 近期保持网格、四分之一圈旋转、承重区和必要通路；逐步增加构件，不承诺任意造型/多层同时落地 | 自由度暂有限，但模板、寻路、存档和碰撞更容易可靠 |
| 后期产业是否要求所有远处船员逐帧行走？ | 近处呈现实体过程；远处将来可按游戏内时段结算，但仍扣真实库存、记录来源与责任 | 需要明确近远切换规则；不要现在做离线收益或全世界实时模拟 |

还有一个表述需要统一：总纲说“第一日即可朝任何方向出发”，开局稿明确木筏受损，`_toggle_sailing()` 也要求风雨过去且筏舷修复。建议明确为“**人可自由探索，受损船需要修复才能航行**”，或另选更开放的起航节奏；这是体验选择，不应由技术条件悄悄决定。

## 二、工程架构：当前有什么，扩展会卡在哪里

主脚本目前约 6100 行，这只用于说明集中程度；**行数本身不是错误**，真正问题是同一处同时负责多种状态与副作用。

| 实际代码证据 | 当前价值 | 后续约束 |
| --- | --- | --- |
| `godot/scripts/ark_greybox.gd`：`_build_world()`、`_interact()`、`_process()`、`_build_save_state()`、`_load_progress()`；`ark_greybox.tscn` 目前主要是挂脚本的根节点 | 原型闭环集中，容易快速做出可玩结果 | 输入、规则、画面、居民和保存彼此直接调用；换模型或加居民也容易触及主控制器 |
| `ark_fixture_placement.gd`：`half_size()`、`supported()`；主脚本 `_fixture_placement_error()`、`_try_move_fixture()` | 已提取几何规则，移动时校验通路、人物与材料不变 | 家具仍主要按 `storage`/`workbench` 类型区分；同类多件、房间模板和床位不能只靠继续加布尔值 |
| 主脚本 `_begin_resident_daily_gather()`、`_process_resident_gathering()` 与 `_process_jade_sail_industry_gathering()` | 有出发、采集、携货、交付、取消阶段及资源争抢复核 | 自家居民与琼华舫各有一套专用流程；前者已有绕障，后者仍直接向目标移动，新增船员会扩大行为差异 |
| 主脚本 `_build_ark_local_walk_route()`、`_build_resident_walk_route()`、`_sail_step()` | 已区分甲板本地路线与岸上世界路线，家可随舟移动 | 路线、船体支撑与设施占地分别计算；自由布置、多层与多船要求更明确的坐标和通行接口 |
| `ark_greybox_save.gd`：`save_state()`、`load_state()`、`_validate_state()`；主脚本 `_load_progress()` | 文件层已有校验、临时写入、备份恢复与未来版本拒绝；玩法层有历史 schema 迁移 | 当前 schema 33 的大量字段仍在主控制器手工映射；存档文件安全与玩法事实正确是两层问题，不能只验证 JSON 合法 |
| `ark_landmass_builder.gd`：`build_island()`；`ark_world_chart.gd`：`refresh()`、`destination_selected` | 地貌构建与地图显示已独立，是值得沿用的拆分方式 | 岛屿信息仍分别出现在 `_build_world()`、`_world_chart_destinations()`、地图 `_draw_map()` 和海面参数中；扩区易漏同步 |
| 主脚本 `_record_world_event()` 与 `MAX_WORLD_EVENTS = 256` | 已记录有来源的事实，避免读档编造剧情 | 限长日志不是永久记忆库，也不能独自重建整个世界；长期蓝图、产权与人物记忆应有独立持久状态 |

**优先级：先明确状态归属和存档/坐标契约，再抽取建造与居民；暂不把“大世界性能”当作已经证实的瓶颈。** 本次没有性能测量，不能据文件大小断言需要 ECS 或更换地形方案。

## 三、三种可选工程方案

| 方案 | 通俗解释 | 收益与代价 | 适用判断 |
| --- | --- | --- | --- |
| A. 保持主控制器，按需提取 | 不搬家，只把常用工具整理到独立抽屉 | 最快、迁移风险较小；但多人、多物件、多船仍会持续增加专用分支 | 若只再验证一个小切片，完全可选；也是 B 的第一步 |
| **B. Godot 场景/Resource 模块化（建议）** | 家具、居民、船有自己的“部件包”；配置写在表里，当前进度另存 | 可在编辑器检查和复用；能逐个替换灰盒美术。需要维护清楚的接口和迁移测试，文件数量会增加 | 最贴合近期家具、居民生活与中后期多舟目标；分批引入，不一次拆完 |
| C. 全面 ECS / 通用模拟框架 | 把所有对象拆成数据小块，再由统一系统批量处理 | 对大量同类对象、明确性能热点可能有价值；但会增加调试、工具、存档映射和学习成本 | **现在后置**。等实测证明目标规模无法满足，再对热点局部采用，不把它当高级架构的必选项 |

Godot 的官方场景组织建议是让子场景少依赖外部细节，由父层提供所需引用；方法用于发起动作，信号用于通知已发生的结果。这支持 B，但不意味着官方替本项目证明了全部设计。[Godot：场景组织](https://docs.godotengine.org/en/stable/tutorials/best_practices/scene_organization.html)

## 四、建议方案具体怎么分工

### 1. “是什么”“现在怎样”“看起来怎样”分开

以储物箱为例：

- **配置 `FixtureDefinition`**：这一类箱子的占地、使用面、材料、模型、功能；基本不随游戏进度变化。
- **状态 `FixtureState`**：这一只箱子的稳定 ID、属于哪条船、甲板位置、朝向、库存引用、损坏情况。
- **场景 `FixtureView`**：模型、碰撞、交互提示和动画；换成正式模型不改这只箱子的身份。

`Resource` 可以理解为 Godot 编辑器可读写的“配置卡”。官方支持自定义资源、属性编辑和 `.tres` 保存；同一已加载资源可能被多个实例共享，因此**不要把各箱子的库存或各居民的伤势写回共享配置**。运行状态可先用有明确字段的对象/字典，继续通过现有 JSON 存档层保存，不必把玩家存档改成 `.tres`。[Godot：Resources](https://docs.godotengine.org/en/stable/tutorials/scripting/resources.html)

### 2. 每项状态只指定一个修改入口

这里的“归属”指谁负责校验和修改数据，不是 Godot 的 `Node.owner` 属性；也不要求下表每行立刻新建一个脚本。

| 游戏对象/系统 | 负责的事实 | 其他系统怎样使用 |
| --- | --- | --- |
| 世界地点、有限资源点 | 地点 ID、位置、剩余量、是否已采集 | 玩家与居民都向同一入口申请采集；不能各自发奖励 |
| 船 `VesselState` | 船位、船体、设施集合、货舱引用、可用床位 | 玩家主舟和琼华舫分别存在；经营权/产权单独记录，不吞并原住居民 |
| 家具/舱室实例 | 类型 ID、实例 ID、船上变换、使用槽位 | 模板只是一次放置多件的方案，落地后仍是普通实例 |
| 居民 `ResidentState` | 身份、居所、工作方针、当前任务、个人事实 | 不在主控制器中无限新增 `某某_boarded`、`某某_target` |
| 工作任务 `JobState` | 执行者、目标、阶段、携货、交付目的地 | 决策只选任务；任务流程处理完成/取消；移动层只负责到达 |
| 库存与交易入口 | 实物数量、预留与转移 | 建造、共餐、交货都重新校验并一次结算，UI 不直接增减材料 |
| 时间/天气与重要事实 | 游戏内时段、天气结果、永久解锁/记忆 | 只有明确入口推进；场景重建与 UI 刷新不能再次结算 |
| 保存服务与显示层 | 保存快照；显示快照/接收通知 | 保存服务不决定剧情，界面不拥有世界事实 |

**近期最低边界**：预览只产生候选方案；确认后统一校验“材料 + 占地 + 通路 + 人物安全”，全部成立再提交。失败和取消不能留下一半家具、一半扣款或提前改路线。当前 `_try_move_fixture()` 的“确认后原地提交”值得保留并推广。

### 3. 稳定 ID、存档和坐标先约定清楚

- **类型 ID ≠ 实例 ID**：`storage` 是一种家具；`fixture_00042` 才是某一只箱子。船、居民、资源点、蓝图各有自己的 ID；显示名称、场景路径、节点名或数组顺序不能当长期身份。继续保留已有资源/人物 ID，不为整洁随意改名。
- **坐标必须带参照物**：船位用世界坐标；家具与船上居民用 `vessel_id + deck_id + local_position + rotation`；岸上居民用世界位置。上岸、登舟或换船时集中转换，不让保存代码根据几个布尔值猜测坐标含义。当前 `_build_save_state()` 中守潮人位置会随采集状态在本地/世界间切换，正说明需要显式约定。
- **路径不是长期事实**：保存目标 ID、任务阶段、携货和位置；读取后按当前场景重算路线。家具搬动、船位变化或目标消失时让路线失效，不保存整条过期路径作为权威。
- **保留文件层，拆出迁移层**：先把旧字典迁成统一状态，再检查关联事实，再重建场景；加载未完成时不让重建函数自动结算或保存半成品。先迁一个子系统，不一次改完所有 schema。
- **重要事实和日志分开**：“已学蓝图、已交货、产权、居民见过什么”长期保存；最近 256 条事件用于解释与调试。不要因为日志滚动删除而忘记人物经历，也不要重放日志重复发奖。

### 4. 居民 AI 与导航不要混为一层

居民 AI 在这里不是大语言模型，而是“**现在做什么、为什么做、受阻怎么办**”。近期用清楚的小状态机即可：空闲 → 去资源点 → 采集 → 携货回舟 → 交货；风暴、启航、资源被先采走则走明确的取消/召回分支。

- **选择任务**：根据时段、天气、方针、可用设施和现存资源挑选；先保持现有可解释规则，不急着加入复杂性格算法。
- **执行任务**：一个居民同时只有一项互斥工作；用目标认领减少两个居民白跑，到达时仍重新检查资源。取消、读取和重复回调不得复制物品。
- **移动到目标**：先保留现有甲板局部 A* 与近岸路线，通过统一接口返回“到达/受阻/取消”；不要为了统一而把琼华舫直线移动误标成完整寻路。
- **以后再选导航实现**：陆地复杂坡面和更多居民可另做 `NavigationAgent3D` 小样；移动甲板仍应单独验证局部坐标、船岸接驳和家具变化。该节点不会自动移动角色，动态避让也不等于寻路或物理碰撞，不能认为“加一个组件就解决全部穿墙”。[Godot：NavigationAgents](https://docs.godotengine.org/en/stable/tutorials/navigation/navigation_using_navigationagents.html)

### 5. 事件和界面只做该做的事

建议用简单方向：`玩家请求 → 规则校验/状态提交 → 已完成事件 → 界面、声音、日志响应`。

例如搬箱子只提交一次 `fixture_moved`；导航据此重算，HUD 据此更新，存档取最终快照。不要让多个信号监听者分别扣材料或各自决定是否成功，也不必先建一个什么都能发的全局事件总线。人物故事只读自己能知道的事实；旧剧情源资产保持档案边界，经审阅再由新呈现层使用，不恢复旧玩法运行时。

## 五、可选择批准的 5 个小 PR

以下是**实施候选**，不是本次已经开始的工作。每个 PR 应独立可回退，沿用 `ARK_ITERATION_PLAN.md` 的协作分支/评审规则；做完一项再决定下一项。

| 小 PR | 严格范围 | 验收条件 |
| --- | --- | --- |
| 1. 固定现状契约 | 加一页 ID/坐标/状态归属约定，补少量特征测试；不改玩法 | 现有家具确认/取消、旋转后航行、居民携货途中保存、重复交货与旧档读取都有明确断言；不以改断言掩盖行为变化 |
| 2. 提取家具存档转换 | 仅提取储物箱/工作台的状态读取、校验和快照转换；保留旧存档格式与文件服务 | 旧档缺省朝向、碰撞兼容和现有材料均不变；读取两次结果一致；坏数据不能让重建中途写回半份进度 |
| 3. 家具配置与场景样板 | 仅把现有两种家具接到共同配置/实例接口；先保留原灰盒视觉，不新增玩法家具 | 同一个配置驱动预览、碰撞占地和使用面；确认/取消/旋转/存读档/居民绕行通过；换一个纯视觉子节点不改 ID 和库存 |
| 4. 提取守潮人采集任务 | 只把现有采集阶段、结算和取消移入可复用任务模块；保留她的对话与方针 | 出工、到达、争抢、携货重载、启航召回、修理互斥保持；测试可用两个临时执行者验证同一资源不双领，但不顺便发布全新居民系统 |
| 5. 地点数据单一来源 | 选一个现有岛屿，把地形参数、海图标记与海岸显示参数接到同一地点定义；不做全图流式加载 | 原有地点/资源 ID 和奖励不变；实走往返、航行碰撞、海图位置和旧档恢复通过；后续扩区可按样板复制配置而非复制主控制器分支 |

这五步不是“完成最终架构”，而是验证 B 是否真的降低下一次改动成本。**多件同类家具、多床位分配、第二位居民营生、多船资产簿分别作为之后的小功能评审**，不能塞进提取 PR。只有出现第二个真实使用场景，才继续概括共性；不要为假想的百人舰队先搭框架。

## 六、验证与美术接入：保护已有投资

### 测试分三层，不互相冒充

1. **规则测试**：占地旋转、材料结算、稳定 ID、迁移、任务重复完成；尽量不必启动整张地图。
2. **场景集成测试**：沿用 `ark_fixture_edit_test.gd`、`ark_resident_gather_test.gd`、`ark_navigation_test.gd`、`ark_world_travel_test.gd`、`ark_jade_sail_industry_test.gd` 和存档审计测试。重点组合：船已旋转/驶离原点、人在通道中、居民携货时存档、目标被抢、家具阻路、取消后再试。现有测试常直接调用主脚本私有函数，提取时保留有用的黑盒结果断言，逐步减少对内部字段名称的绑定。
3. **实际画面与性能**：使用项目已有 `tools/verify_godot.py` 的逻辑/打包检查与独立渲染入口；固定机位检查日夜、风雨、屋内遮挡、模型尺度、玩家和居民的移动手感，并在目标设备记帧时间。headless 通过不代表画面好看，截图也不代表任务不会重复结算。

本报告只确认存在上述代码/测试机制，**不声称这些检查在本次已通过**。实际运行、Windows 导出与 CI 状态以各自证据为准。

### 美术先做一个可替换样板

- 遵循现有计划：先一处海岸、一段甲板、一间居室，不全世界同时换皮。当前 `project.godot` 使用 GL Compatibility；候选材质、光照和特效必须在这个实际后端验证，不顺手改渲染路线。
- 模型放在独立视觉子场景下；交互锚点、碰撞、家具功能与稳定 ID 由游戏侧保留。角色另需骨架、动作和脚底接地验证，概念图不能算可动角色交付。
- 每份资产保留来源、作者、许可证、允许修改/再分发条件、尺度、导入设置和使用记录。先验证资源再进口，不把开源代码许可等同于附带美术许可。
- Godot 提供 3D 场景导入、导入配置和继承场景流程；可用它们保留源模型再导入能力，而不是把玩法脚本直接绑死到某个模型内部节点。[Godot：3D 场景导入](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/index.html)

## 最后建议
